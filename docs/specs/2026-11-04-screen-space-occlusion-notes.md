## 1. 为什么需要它

视口里物体和地面接触的地方没有暗部，所有面按同一个半球光照受光，于是建筑物、池体、
设备都像**浮**在地上。这是"塑料感"最直接的来源，比贴图分辨率影响大得多。

烘焙方案（把 AO 写进顶点色）对模型库是划算的，但 Studio 是建模工具：几何会被反复修改，
烘焙结果每次都失效。因此选择实时屏幕空间方案；烘焙留作未来对"完工资产"的可选增强。

## 2. 一次失败的尝试（2026-11-04）

### 做了什么

参照 `WebGL2ShadowMap` 的结构新增 `WebGL2SceneDepth`：深度 FBO（`DEPTH_COMPONENT24`）、
只写深度的极简着色器、随视口重建纹理；主着色器里加 8 方向 × 2 圈深度比较，邻居更靠近
相机就把间接光压暗。编译通过，webpack 构建成功。

### 结果

```
AO 前：meanLuminance 99.19 / brightPixels 991
AO 后：meanLuminance 99.19 / brightPixels 991   ← 一个像素都没变
```

### 排查与根因

1. 先怀疑只有深度附件的 FBO 在 WebGL2 里不完整，补了 `gl.drawBuffers([gl.NONE])` 与
   `gl.readBuffer(gl.NONE)`——**画面依旧完全一致**。
2. 真正的原因：深度 pass 只绘制了**实例化批次**（照抄阴影 pass 的循环），而控制台的瓦片
   集通过 `ICERenderBatch` 走的是**渲染批次**路径。深度图是空的 → 采样恒为 0 →
   所有比较相等 → 遮蔽恒为 0。

### 结论

`WebGL2RendererBackend.render()` 里有八处绘制循环（实例化批次、渲染批次、单体网格，
以及阴影/选择/拾取各自的变体）。**任何新增的屏幕空间通道都必须覆盖全部三条几何路径**，
试图"只复制一条路径、不碰原有代码"来省掉重构是行不通的——本笔记即为反例。

改动已全部回退；惰性代码（跑着但不生效）不应入库。

## 3. 正确顺序

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | 把三条几何路径的绘制抽成可复用遍历 `drawScene(program, pass)` | 同机位截图**逐像素一致** |
| 2 | 深度 pass 覆盖三条路径（渲染批次需按节点算 MVP） | 深度图非空：把深度可视化，应能看出轮廓 |
| 3 | 加 SSAO，半径按视距缩放 | 同机位 A/B 像素差 > 2%，接触处明显压暗 |
| 4 | 调参（半径、采样数、强度），在 SwiftShader 上确认可接受帧率 | 交互仍流畅 |

第 3 步的半径必须随视距变化：厂区跨度 600 米，写死世界半径会让近景糊、远景无感。

## 4. 边界

- 只覆盖实例化批次与渲染批次里**不透明**的几何；透明面不参与深度写入
- AO 只压暗间接光，不改变直射与自发光
- 屏幕空间方法的固有限制：画面外的遮挡物不可见、掠射角易出现条带，需要配合强度上限
